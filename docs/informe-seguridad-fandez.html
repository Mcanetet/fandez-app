2. Resumen ejecutivo

Fandez es una plataforma de servicios del hogar con pagos reales, datos personales, documentos KYC y chat en vivo. La seguridad se organiza en tres capas:

  1. Prevención — contraseñas con bcrypt, HTTPS, Helmet/CSP, roles, CSRF en admin, rate limit, panel admin en path secreto, MFA, validación de archivos.
  2. Detección — logs de seguridad, Hostinger Vulnerabilities (Patchstack npm), backups cifrados, alertas SOS / Sofía, correo de soporte.
  3. Respuesta — este playbook: pasos concretos según el tipo de amenaza (malware, cuenta comprometida, defacement, ransomware, DDoS, etc.).
Importante

Ningún sitio es 100 % invulnerable. Este documento te prepara para actuar rápido, contener el daño y recuperar el servicio con evidencia. Si hay peligro físico a personas, prioriza 133 (Carabineros) — eso está en el protocolo de seguridad en terreno, no sustituye a este informe técnico.

5. Plan de respuesta — qué hacer en cada caso

Usa siempre este orden: 1 Contener → 2 Evidencia → 3 Erradicar → 4 Recuperar → 5 Aprender.

5.1 Severidad

S1 Crítico datos robados, ransomware, defacement, pagos manipulados, admin comprometido
S2 Alto malware en upload, cuenta de socio/cliente hackeada, CVE explotable
S3 Medio escaneo, spam, DDoS leve, falso positivo Hostinger

Primera hora (cualquier S1)
  1. No borrar logs ni “arreglar a ciegas” sin capturas.
  2. Anotar hora (Chile), qué viste, IP si aparece, usuario afectado.
  3. Si hay filtración de datos personales: preparar aviso a afectados (Ley 19.628 / buenas prácticas) — contactar abogado si el volumen es alto.
  4. Cambiar SESSION_SECRET y contraseñas admin solo después de contener (ver casos abajo).

Caso A — Hostinger avisa vulnerabilidades npm S2

  1. Abre hPanel → Security → Vulnerabilities y anota paquetes/CVE.
  2. En el Mac: npm audit --omit=dev en el repo.
  3. Actualiza versiones seguras (sin --force a ciegas).
  4. Commit + push a main + Redeploy.
  5. Verifica que el panel Hostinger quede en cero.

Caso B — Intento de fuerza bruta / login masivo S3–S2

  1. Revisa security_logs en admin y Runtime logs Hostinger.
  2. Confirma que rate limit sigue activo (429 en demasiados intentos).
  3. Si persiste: activa/ajusta ADMIN_IP_ALLOWLIST; cambia contraseña admin; activa MFA.
  4. No abras enlaces de “reset” que lleguen por correo sospechoso.

Caso C — Cuenta de cliente/socio/técnico comprometida S2

  1. En admin: desactiva la cuenta (active=false) — corta sesión.
  2. Revisa pedidos recientes, chats y pagos de esa cuenta.
  3. Contacta al dueño legítimo por un canal verificado (no solo el email de la cuenta).
  4. Tras limpiar: reset de contraseña + reactivación controlada.
  5. Si hubo cobros indebidos: abrir disputa en Mercado Pago / banco y documentar.

Caso D — Sospecha de admin hackeado S1

  1. Desde Hostinger: reinicia la app o pon mantenimiento si es posible.
  2. Rota de inmediato: SESSION_SECRET, ADMIN_PASSWORD, ADMIN_PATH (nuevo path), tokens MP/SMTP, BACKUP_SYNC_TOKEN.
  3. Redeploy desde GitHub main limpio (no uses archivos raros del servidor).
  4. Revisa usuarios admin, MFA, allowlist IP.
  5. Audita cambios recientes en BD (precios, promos, usuarios).

Caso E — Virus / malware en archivo subido (foto, boleta, PDF) S2

  1. No abras el archivo en tu PC personal sin sandbox.
  2. En admin: identifica el pedido/usuario y elimina o aisla el archivo en uploads.
  3. Desactiva temporalmente al usuario que lo subió si hay mala fe.
  4. Verifica que el tipo MIME/extensión siga restringido (JPG/PNG/WEBP/PDF).
  5. Si el archivo se ejecutó en algún lado (poco probable en Node sirviendo static): trata como Caso G.

Caso F — Página defaceada / HTML raro / redirects a phishing S1

  1. Redeploy limpio desde GitHub (sobrescribe archivos infectados del deploy).
  2. Cambia todos los secretos de entorno (ver Caso D).
  3. Revisa DNS del dominio en Hostinger (que no apunte a otro lado).
  4. Escanea el correo corporativo (SMTP) por reglas de reenvío desconocidas.
  5. Avisa a usuarios solo si hubo phishing activo con datos.

Caso G — Código malicioso en el servidor (shell, crypto-miner) S1

  1. Redeploy desde GitHub + rotación total de secretos.
  2. Revisa procesos / CPU en Hostinger; contacta soporte Hostinger si la carga es anormal.
  3. Compara el árbol de archivos del deploy con el repo (no debe haber PHP/shell sueltos).
  4. Rota claves MySQL si hay duda de acceso a BD.
  5. Restaura desde backup cifrado solo si el código limpio + BD sospechosa.

Caso H — Ransomware / BD cifrada o borrada S1

  1. No pagues rescate sin asesoría legal.
  2. Detén escrituras si puedes; exporta lo que quede.
  3. Recupera el último backup bueno: rama GitHub backups + decrypt-github-backup.js.
  4. Redeploy app limpia + restore BD en entorno controlado.
  5. Rota todas las claves; investiga vector de entrada.

Caso I — Filtración de datos personales (PII) S1

  1. Contén el acceso (Casos C/D/G según origen).
  2. Documenta qué datos salieron (emails, RUT, direcciones, documentos KYC).
  3. Avisa a afectados con hechos claros (qué, cuándo, qué hacer ellos: cambiar clave).
  4. Conserva evidencia (logs, backups) — no la borres.
  5. Consulta abogado/compliance si el impacto es masivo.

Caso J — Pagos manipulados / cobros fantasma S1

  1. Congela el pedido en admin; no reembolses a ciegas sin ver MP.
  2. Revisa panel Mercado Pago / Transbank vs. pedido en Fandez.
  3. Verifica MP_WEBHOOK_SECRET y que los webhooks no se estén reenviando a otro lado.
  4. Si hay fraude de tarjeta: sigue el proceso del adquirente (contracargo).

Caso K — DDoS / sitio caído por tráfico S2

  1. Confirma en Hostinger (CDN hcdn) y /health.
  2. Activa/valida rate limit; pide a Hostinger mitigación CDN si aplica.
  3. No abras puertos ni desactives HTTPS “para probar”.
  4. Cuando vuelva: revisa logs de IPs top y bloquea si es repetitivo.

Caso L — Phishing / virus en el correo del equipo S2

  1. No descargues adjuntos ni des permisos OAuth a sitios raros.
  2. Cambia contraseña del buzón Hostinger; revisa reenvíos y filtros.
  3. Si se filtró SMTP_PASS: rota la clave SMTP en la app y reinicia.
  4. Avisa al equipo: el admin real nunca pide la contraseña fuera de la app.

Caso M — Bug explotado (XSS, IDOR, lógica de negocio) S2–S1

  1. Reproduce en staging o local; no ignores reportes de usuarios.
  2. Parchea en el repo; tests mínimos; deploy.
  3. Revisa si alguien abusó el bug (pedidos/pagos) y revierte efectos.
  4. Agradece reportes responsables; no publiques detalles hasta parchear.

Caso N — Compromiso de GitHub S1

  1. Revoca tokens/PAT; activa 2FA en GitHub si no está.
  2. Revisa commits recientes en main; revertir lo malicioso.
  3. Rota secrets de Actions (FANDEZ_BACKUP_*).
  4. Redeploy solo desde commit verificado por ti.
Recuperación estándar post-incidente
  1. Redeploy limpio desde main.
  2. curl -s https://www.fandez.cl/health → ok: true.
  3. Login admin + prueba de un pedido demo/pago sandbox si aplica.
  4. Anotar en un registro interno: fecha, caso, acciones, responsable.
  5. Programar mejora (parche, monitoreo, MFA) en la semana siguiente.
